# 设计方案：从「别人的看板」到「自己的看板」

> 配套文档：[01-网站分析.md](01-网站分析.md)（对目标站点的逆向分析）

---

## 1. 需求收口

你的原话：

> 只想做自己的看板，方便自己查看**多周期形态**、**多种技术分析结果**。
> 费率套利用不到，多空战场不需要。

据此砍掉了原站 70% 的功能，只保留三条主线：

| 保留 | 砍掉 | 理由 |
|---|---|---|
| 多周期 K 线与形态 | 多空战场 2D/3D | 游戏化对你无用 |
| 多指标技术分析 | 费率套利 | 明确不需要 |
| 多周期共振判断 | 12 所清算流、聚合订单簿、Deribit 期权、ETF/稳定币宏观 | 单所（Binance）数据已足够做技术分析 |
| — | AI 分析、会员体系、PWA 推送、广告位 | 个人工具不需要 |

**核心判断：技术分析不需要 12 个交易所的数据。** 原站聚合 12 所是为了清算地图和套利，这两个你都不用。用 Binance 一家，数据更干净、延迟更低、口径统一（不会出现原站那种「现货价冻结在 75845、合约 73940」的污染）。

## 2. 一个关键约束：网络

这台机器在国内，直接连交易所全部失败：

```
api.binance.com  → 31.13.83.34      （Facebook 的 IP，DNS 污染）
www.okx.com      → 169.254.0.2      （链路本地地址，污染）
```

但机器上跑着本地代理 `127.0.0.1:7897`。实测通过它可以拿到：

| 交易所 | 直连 | 经代理 |
|---|---|---|
| Binance 现货/合约 | ✗ | ✓ 195 ms |
| Bybit | ✗ | ✓ 248 ms |
| Bitget | ✗ | ✓ 189 ms |
| Gate | ✗ | ✓ 585 ms |
| Deribit | ✗ | ✓ 331 ms |
| OKX / Coinbase | ✗ | ✓（需带浏览器 UA，否则 403） |

**所以工具内置了「通道自适应」**：启动时先试直连（1.5 秒超时），失败自动切代理，之后固定。
这意味着同一份代码，放在没有墙的服务器上也能直连跑，不用改配置。

> 顺带记一个坑：`curl` 走代理时会失败（`schannel: AcquireCredentialsHandle failed`），
> 那是 Windows Schannel 在沙箱里拿不到证书凭证，**不是网络问题**。
> Python 用自己的 OpenSSL，正常。所以抓取层必须用 Python 而不是调用 curl。

## 3. 技术选型

| 决策 | 选择 | 理由 |
|---|---|---|
| 后端 | Python 3.12 **标准库** `ThreadingHTTPServer` | 机器上没装 fastapi/requests；单用户不需要 ASGI；标准库永不过期 |
| 前端 | 原生 JS + lightweight-charts 4.1.3 | 无构建步骤，改完刷新即见；图表库 MIT 且只有 160 KB |
| 指标计算 | **服务端** numpy | 与前端解耦、口径统一、便于以后接 AI；numpy 已在环境里 |
| 传输 | REST + gzip，轮询 | 不需要 WebSocket（不看清算流），20 秒轮询足够 |
| 缓存 | 内存 TTL + 落盘快照 | 断网时仍能看图，不至于白屏 |
| 鉴权 | **不做** | 只监听 `127.0.0.1`，本机专用 |

**为什么不用 FastAPI**：它的价值在异步 IO、依赖注入、自动文档、并发。这是单人本机工具，6 个只读端点，`ThreadingHTTPServer` 完全够，还省掉 `pip install` 和版本漂移。

## 4. 多周期共振模型

这是整个工具的**核心设计**，也是原站没有的东西（原站只是把 6 个周期并列显示，没有聚合判断）。

### 4.1 单周期打分

每个周期产出 17~18 条信号，每条有 `方向 ∈ {-1,0,+1}` 和 `权重 ∈ [0.4, 1.5]`：

```
score = 100 × Σ(方向 × 权重) / Σ(权重)        ∈ [-100, +100]
```

阈值：

| 分数 | 判定 |
|---|---|
| > 55 | 强多 |
| 20 ~ 55 | 偏多 |
| -20 ~ 20 | 中性 |
| -55 ~ -20 | 偏空 |
| < -55 | 强空 |

### 4.2 跨周期聚合

```
加权分 = Σ(各周期 score × TF_WEIGHT) / Σ(TF_WEIGHT)

TF_WEIGHT: 1w 2.2 > 1d 2.0 > 4h 1.6 > 1h 1.3 > 30m 1.0 > 15m 0.8
```

大周期权重更高 —— 因为「顺大势」比「抓小反弹」重要。

同时单独算出 **大周期分**（只看 4h/1d/1w），用来回答另一个问题：**小周期反弹是不是逆着大趋势？**

### 4.3 共振判定

```
同向周期数 ≥ 5  → 强共振
同向周期数 ≥ 3  → 部分共振
有反向周期      → 多周期分歧
```

方向阈值 ±8，避免把噪声当成趋势。

### 4.4 为什么用「加权投票」而不是「K 线对齐」

另一种思路是找 6 个周期上同时满足的形态（比如都出现 MACD 金叉）。问题是：
- 形态在不同周期的定义不一致（15m 的「大阳线」在 1w 上不是）
- 罕见到几乎不触发

加权投票虽然粗糙，但**每个周期都在说话，权重透明可调**，而且能直接看到「谁在反对」。对个人决策来说，知道「1d 强空但 15m 偏多」比知道「有一个共振信号」更有用。

## 5. 形态识别

### 5.1 K 线形态（14 种）

按「实体比例 + 影线比例 + 连续性」判定，全部带置信度：

```
锤子线   ：下影 ≥ 实体×2，上影 ≤ 实体×0.6，阳线
射击之星 ：上影 ≥ 实体×2，下影 ≤ 实体×0.6，阴线
吞没     ：本根实体完全包住前一根，且方向相反
早晨之星 ：阴 → 小实体 → 阳（收回前一根一半以上）
红三兵   ：连续三根阳线且收盘递增
...
```

### 5.2 图表形态（9 种）

用**分形法**找摆动高低点（左右各 3 根），再判定：

```
双底   ：两个低点相差 < 2%，间隔 ≥ 5 根
三角收敛：高点下移 + 低点上移
通道   ：高低点同向移动
突破   ：收盘越过前 20 根的高低点
跳空   ：本根最低 > 前根最高（或反之）
```

### 5.3 互斥去重（原站的坑）

原站会出现「同时检测到双底和双顶 + 上升通道」这种自相矛盾的输出。
本工具对互斥形态组只保留 **idx 最新、置信度最高** 的一个：

```python
_EXCLUSIVE = (
    {"double_bottom", "double_top"},
    {"channel_up", "channel_dn", "triangle"},
    {"gap_up", "gap_dn"},
    {"breakout_up", "breakout_dn"},
)
```

## 6. 指标口径验证

指标算错的话，后面全是错的。所以做了**交叉验证**：

| 校验项 | 方法 | 结果 |
|---|---|---|
| MA20 / MA60 | 与 `np.mean(c[-20:])` 逐位比 | ✓ 一致 |
| BOLL | 中轨 == MA20，上轨 == 中轨 + 2σ | ✓ 一致 |
| MACD | 恒等式 `hist == 2×(DIF−DEA)` | ✓ 一致 |
| RSI14 | 独立实现 Wilder 平滑后比对 | ✓ 一致 |
| **与原站比对** | ADX / ATR / Aroon 末值 | **逐位一致** |

最后一项是最强证据：我的 `ADX = 16.90429395370003`、`ATR = 447.7531193102021`，
与原站 `/api/klines` 返回的 `16.90429395370003` / `447.7531193102021` **完全相同**。
说明虽然独立实现，但口径和主流软件对齐。

## 7. 性能设计的取舍

原站的致命问题是「每次请求都全量重算 1006 根 K 线的 25 组指标，前端每秒拉一次」。

本工具的做法：

| 措施 | 效果 |
|---|---|
| `limit` 参数**真的生效** | 只返回 320 根（够画图），不是 1006 根 |
| 指标只算一次，缓存在内存 | 同周期重复请求命中缓存 |
| 只返回前端要用的序列 | 不是 25 组全给 |
| gzip | 143 KB → 63 KB |
| 前端 **20 秒**轮询 | 不是 1 秒 |
| 6 个周期**并行**计算 | 冷启动 1.5 s → 0.39 s |
| 启动时预热通道 + 默认标的 | 首屏 6.9 s → 0.3 s |
| 页面隐藏时停止轮询 | 切到后台不再耗流量 |

净效果：

| | 单次体积 | 频率 | 折算 |
|---|---|---|---|
| 图表 | 63 KB | 20 秒 | 11.3 MB/h |
| 共振 | 5.4 KB | 45 秒 | 0.4 MB/h |
| 行情/健康 | <1 KB | 10~30 秒 | 0.1 MB/h |
| **合计** | | | **≈ 12 MB/小时** |

原站约 **3.1 GB/小时**，相差约 **260 倍**。

> 这不是炫技 —— 原站那个量级，一个用户就能把服务器 CPU 吃满；
> 你这个虽然只有你一个人用，但笔记本上跑一个持续 3 GB/小时的页面，风扇也会响。

## 8. 与原站的对比

| 维度 | 原站 | 本工具 |
|---|---|---|
| 数据源 | 12 所聚合（实际 4 所有清算） | Binance 单所（现货/合约可切） |
| 周期 | 6 个，并列展示 | 6 个，**合并成共振结论** |
| 指标 | 25 组，全量返回 | 30 个，**只返回需要的** |
| 形态 | 只有 2 个模糊的「候选」标签 | **23 种明确形态 + 置信度 + 图表标注** |
| 判断 | 无（只给数据） | **加权打分 + 共振判定 + 一句话结论** |
| 鉴权 | 前端遮罩（19 个端点裸奔） | 不做（只监听本机） |
| 并发 | 4~6 用户打满 | 单用户，无需考虑 |
| 依赖 | Python + 若干未知包 | 零第三方依赖 |

**保留借鉴的**：
- 指标算在服务端、前端只渲染
- 「最新值扁平对象」同时供面板和未来 AI 使用
- 自研 Markdown 流式渲染的思路（本工具暂未用 AI，留作扩展点）

**刻意不做的**：
- 清算地图（需要多所 + 杠杆分布反推，误差大且你不需要）
- 聚合订单簿（`/api/book` 单次 2.9 MB / 18 秒，性价比极低）
- 会员/广告/推送（个人工具）

## 9. 后续可扩展的点

按性价比排序：

1. **多空信号历史回测** —— 现在有打分，可以记录每次「强共振」出现后的实际走势，验证这套权重是否真的有效。这是最有价值的一步。
2. **自定义权重** —— 把 `TF_WEIGHT` 和信号权重放到前端可调，边看边试。
3. **形态提醒** —— 检测到「双底 + 底背离 + 超级趋势翻多」这种组合时，标红。
4. **多所交叉验证** —— 同样的分析跑 Bybit/Bitget，三个所方向一致才出信号（利用已有的代理通道）。
5. **AI 分析** —— 把 `snapshot` + `signals` 喂给模型生成研判。接口已预留（`analysis.analyze()` 的输出就是完整的结构化输入）。

## 10. 已知限制

- **只用了 Binance 一家**。Binance 宕机或极端行情下价格异常时，看板会跟着异常。想要交叉验证见上一节第 4 点。
- **周线数据不满 250 根以前，MA200 为空**。已做 NaN 处理，不参与打分。
- **形态识别是规则式的**，不理解上下文（比如不知道这个双底发生在长期下跌末端还是震荡中段）。置信度只是启发式。
- **共振权重是拍出来的**，没有回测验证。所以叫「参考结论」，不叫「交易信号」。
- **依赖本地代理**。代理挂了会退化到落盘快照（顶部显示「数据快照」），此时数据是旧的。
